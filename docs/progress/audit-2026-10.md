## Production upgrade (recommendation, not executed)

Production (2026-10-18): `back` 1.0.79, `django_resaas` 0.0.659; `OTP_KEY` and `URL_FILE_KEY` rotated, `DEBUG=0`. Still open in pro: `/media/` served by an nginx alias (no token), the unused `Organization Administrator` Group (0 members) to delete.
Target: `django_resaas` >= 0.0.659 (0.0.660 when released) with `back` >= 1.0.79 (it declares
`django_resaas>=0.0.659`) and a `front` validated against it.

1. **Before anything**: rotate `OTP_KEY` and `URL_FILE_KEY` (#2) and set `DEBUG=0` (#4). These close
   the live attacks without a deploy.
2. **Read** `django_resaas/docs/deployment/upgrading.md`, sections 0.0.658, 0.0.659 and the entries
   of "next release after 0.0.632" released after 0.0.646. Breaking for clients: `files/`, `branchs/`,
   `branchusers/`, `branchusergroups/` now need their permissions and stay in the current Entity;
   `mail/` and `password/change/mobile/` are aliases of the hardened reset flows. Grant the
   permissions to the profiles that need them (in the profile files, then `migrate`).
3. **Back up** the `pro` database (`make dbbackup`) and the `pro/venv` package list (`pip freeze`).
4. Upgrade `pro/back` to the validated tag, `pip install "django_resaas==<version>"`, run
   `python manage.py migrate` (framework migrations 0005-0008: `entity.google_place_id`,
   `theme.owner`; 0006 adds and 0008 removes `entity_type.site`), `resaas_setup`, then restart
   `gunicorn_pro_back`.
5. Smoke test: login, context switch, one CRUD per module, a file download, a PDF.
6. **Rollback**: reinstall the previous `django_resaas` **only** if no new migration ran; once 0005-0008
   ran, restore the database backup together with the previous package and `back` tag. Never install
   an older package over migrations that already ran.
