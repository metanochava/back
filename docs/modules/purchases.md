# The `purchases` module

`purchases` (`back/purchases`) records what an Entity buys: **suppliers**,
**purchase orders** with their lines, the **approval** of an order, and the
**goods receipts** delivered against it. A receipt moves stock in through the
`inventory` module when that module is active; without it the receipt is still
recorded.

It is a horizontal module, like `sales` and `inventory`, and knows nothing about
Health, the pharmacy or any vertical: a hotel, a school or a shop buys the same
way.

- `MY_APPS`: `'purchases'`. It is not a default module: Root activates it per
  Entity (App catalogue / `EntityApp`), and every endpoint answers `403` while it
  is inactive.
- API: `/api/purchases/<resource>/`, all `BaseAPIView` (PROTECTED: module active,
  tenant context, one permission per action).
- Depends on `django_resaas` only. `inventory` is optional: it is used through
  `inventory.services` (its public interface), never its models, and only when
  installed and active.

## Models

| Model | What it is |
|---|---|
| `Supplier` | `supplier_type` `individual` (a `Person`, whose name/e-mail/phone are not copied) or `company` (`company_name`); `tax_id`, `email`, `phone`, `address`, `payment_terms` (days), `active`, `notes`. |
| `PurchaseOrder` | `number` (`PO-<year>-<sequence>`, per Entity), `supplier`, `warehouse_id` (loose reference to `inventory.Warehouse`), `order_date`, `expected_date`, `supplier_reference`, `status`, `total`, `notes`, and the audit fields `submitted_*`, `approved_*`, `cancelled_*`, `cancel_reason`. |
| `PurchaseOrderLine` | `order`, `product_id` (loose reference to `inventory.Product`, with a `product_name`/`product_code` snapshot) **or** a free `description` (a service, or an Entity without inventory), `quantity`, `unit_cost`, `received_quantity`. Read-only computed: `line_total`, `outstanding_quantity`. |
| `GoodsReceipt` | One delivery: `order`, `warehouse_id`, `stock_tracked`, `received_at`, `notes`, `idempotency_key`. |
| `GoodsReceiptLine` | `receipt`, `order_line`, `quantity`, `unit_cost` (copied from the order line). |

All are `BaseModel` (Entity + Branch, soft delete, `created_by`/`updated_by`).
Status, numbers, totals, snapshots, `received_quantity` and the audit fields are
read only in the API: `purchases/services.py` writes them.

## Workflow

```
draft ──submit──▶ submitted ──approve──▶ approved ──receive──▶ partially_received ──receive──▶ received
  ▲                   │                     │                          │
  └──return_to_draft──┘                     │                          └──receive (until nothing is outstanding)
draft / submitted / approved ──cancel (reason required)──▶ cancelled
```

- The header and its lines can be changed or deleted only while the order is
  `draft` (`409 purchase_order_not_draft` otherwise).
- `submit` needs at least one line. `cancel` needs a reason and is refused once
  anything was received (an order with receipts can only be completed).
- Every transition re-reads the order with `select_for_update()`, so two
  concurrent requests cannot both pass the same check. A transition the status
  does not allow is `409 invalid_status_transition`.
- Events (`EventDispatcher`, for notifications or integrations):
  `purchases.order.submitted`, `purchases.order.approved`,
  `purchases.order.cancelled`, `purchases.receipt.posted` (context: `order_id`,
  `order_status`, `stock_tracked`).

### Receiving goods

`POST /api/purchases/purchaseorders/{id}/receive/`

```json
{
  "lines": [{"line": "<PurchaseOrderLine id>", "quantity": "4"}],
  "warehouse_id": "<inventory.Warehouse id, optional - defaults to the order's>",
  "notes": "Delivery note 1234",
  "idempotency_key": "<uuid generated by the client per attempt>"
}
```

Answer `202` with `{"receipt": {...}, "order": {...}}`. In one transaction:

1. each line must belong to the order, appear once, and have `0 < quantity <=
   outstanding` (`400 invalid_receipt_line` / `invalid_quantity`,
   `409 over_receipt`);
2. the `GoodsReceipt` and its lines are created and `received_quantity` grows;
3. when the Entity has `inventory` **active** and a warehouse is known,
   `inventory.services.commit_purchase_receipt_movements()` creates an inbound
   `StockMovement` (type `entrada`, `custo_unitario` = the line's cost,
   `documento_origem_tipo="purchase_receipt"`) per product line, and
   `stock_tracked` is `true`. Lines with only a description never move stock;
4. the order becomes `partially_received` or `received`.

Any failure rolls everything back: no receipt, no movement, no quantity change.
Repeating a request with the **same `idempotency_key`** (double click, retry
after a timeout) returns the first receipt instead of receiving twice.

Receipts are read only (`GET` only, `405` otherwise): a correction is a future
return document, never an edit.

## API

| Method | Route | Permission |
|---|---|---|
| `GET/POST` | `/api/purchases/suppliers/` | `list_supplier` / `add_supplier` |
| `GET/PATCH/DELETE` | `/api/purchases/suppliers/{id}/` | `view_` / `change_` / `delete_supplier` |
| `GET/POST` | `/api/purchases/purchaseorders/` | `list_purchaseorder` / `add_purchaseorder` |
| `GET/PATCH/DELETE` | `/api/purchases/purchaseorders/{id}/` | `view_` / `change_` / `delete_purchaseorder` (draft only) |
| `POST` | `.../purchaseorders/{id}/submit/` | `submit_purchaseorder` |
| `POST` | `.../purchaseorders/{id}/return_to_draft/` | `return_to_draft_purchaseorder` |
| `POST` | `.../purchaseorders/{id}/approve/` | `approve_purchaseorder` |
| `POST` | `.../purchaseorders/{id}/cancel/` (`{"reason"}`) | `cancel_purchaseorder` |
| `POST` | `.../purchaseorders/{id}/receive/` | `receive_purchaseorder` |
| `GET/POST` | `/api/purchases/purchaseorderlines/` (`?order=<id>`) | `list_` / `add_purchaseorderline` |
| `GET/PATCH/DELETE` | `/api/purchases/purchaseorderlines/{id}/` | `view_` / `change_` / `delete_purchaseorderline` (draft only) |
| `GET` | `/api/purchases/goodsreceipts/` (`?order=<id>`), `/goodsreceiptlines/` | `list_` / `view_goodsreceipt(line)` |

Errors follow the RESAAS contract (`{"error": {"code", "message", "details"}}`),
messages translated with the request language.

## Multi-tenancy and security

- Every list and detail is scoped to the current Entity by `BaseAPIView`;
  another Entity's id answers `404`, including on the actions.
- A `supplier` or `order` of another Entity is refused by
  `TenantRelationsMixin` (`400`). The loose references are checked by the
  module: `product_id` must be one of the Entity's products
  (`inventory.services.get_product_snapshot(id, entity_id=...)`), `warehouse_id`
  one of its warehouses (`get_warehouse_snapshot`, `400 invalid_warehouse`), and
  `commit_purchase_receipt_movements` looks both up inside the Entity again.
- Approving and receiving are separate permissions from buying, so a profile can
  order without approving, or receive without ordering.
- Approval can be driven by a [workflow](workflow.md) (`purchases.approve_order`
  registered action); while one is pending, `approve` answers
  `409 approval_workflow_pending`.

## Profiles (`purchases/profiles.py`)

Granted by `group_creator()` after `migrate` (additive):

| Profile | Gets |
|---|---|
| Purchasing Manager | everything, including approve, cancel and receive |
| Buyer | suppliers, orders and lines, `submit` - not approve, not receive |
| Warehouse Manager, Receiving Clerk | read orders, `receive_purchaseorder`, receipts |
| Finance Manager | read, `approve_purchaseorder` |
| Accountant, Auditor | read only |

Root receives the five action permissions in `purchases/signals.py`. The names
are the same profiles the other modules use (no per-module duplicates).

## Frontend (`front/src/pages/purchases`)

- `list_supplier`, `list_goodsreceipt`: `s-auto-crud` driven by the schema.
- `list_purchaseorder`: list with search and a **New purchase order** dialog
  (supplier, warehouse when the user can list warehouses, expected date,
  reference, notes) that opens the order.
- `view_purchaseorder/:id`: header, lines (add/remove while draft, product from
  inventory or a description), receipts, and the action buttons, each shown only
  with its permission and status. **Receive goods** opens a dialog with the
  outstanding quantity of each line and sends one `idempotency_key` per opened
  dialog. Buttons are UX only: the backend decides.
- Stores: `purchaseOrderStore.js` (`BaseStore` + the domain actions),
  `purchaseOrderLineStore.js`, `goodsReceiptStore.js`.

## Tests

`purchases/tests`: API contract and derived fields, state machine, receiving
(partial, over-receipt, invalid lines, idempotency), stock integration (inbound
movement with cost, another Entity's warehouse/product, inventory inactive),
tenant isolation, module inactive, permission per action, profiles and
translations.
